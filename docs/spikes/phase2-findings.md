# Phase 2 findings

Date: 2026-10-06. Platform: Ignition 8.3.9 Maker Edition in Docker (hub and site1 gateways), Windows 11 host. Numbering
continues from [phase1-findings.md](phase1-findings.md). These findings test the guesses listed in
[ADR 0014](../adr/0014-phase2-fleet-shape-simulators-oem-reads-inheritance-battery.md).

| # | Question | Answer | Where it matters |
|---|---|---|---|
| 36 | What do a hub's Remote Tag Provider settings look like, and can the hub's name differ from the site's provider name? | Wes built the provider by hand in the hub's Config pages. Read back through the REST API it is type `REMOTE` with `serverName` `site1` (the gateway's name on the Gateway Network), `remoteProviderName` `default`, `historyMode` `GatewayNetwork`, `alarmStatusEnabled` true, and `alarmMode` `Queried`. The hub's own name for it (`site1`) differs from the remote name (`default`), so the guess in ADR 0014 holds. Before the provider existed, `GET /gateway-network/remote-tag-providers/site1` already listed site1's two providers, `System` and `default`. The 8.3 documentation lists Name and Provider as separate fields and says a remote provider is read only by default (Default Security Zone); that last point is from the documentation and has not been tested here. | ADR 0014 decision 4; Layer Card 3 |
| 37 | Does the hub hold a copy of a remote provider's tags? | No. Listing the hub's `config/resources/core/ignition/tag-definition` folder showed only `default` and `System`, with no `site1`. In Designer, Inv1's `ACPower_kW` read about 1,100 kW on the hub and the same on site1. The provider's `tagCount` metric reads 121, and a scratch provider created seconds earlier showed 121 as well, so it counts what the hub can see through the link and not tags it stores (my reading of the metric). | Layer Card 3 (how the hub sees the fleet) |
| 38 | Can the REST API create a remote tag provider? | Yes. `POST /data/api/v1/resources/ignition/tag-provider` with a list holding `{name, enabled, description, config}` created a scratch provider, `scratch-remote`, using the hand-built provider's own `config` as the body. It reported healthy (`Running`) on the first check and showed 121 tags. It was removed with `POST /resources/delete/ignition/tag-provider` and `{name, signature}`, and the hub went back to `System`, `default`, and `site1`. The provider resource type offers three kinds: `MANAGED`, `REMOTE`, and `STANDARD`. Not tested: creating `STANDARD` providers (the OEM sites' own providers) and whether Maker limits how many providers one gateway may have. | Generator (Site 2 and OEM providers); ADR 0014 decisions 4 and 5 |
| 39 | Does the REST tag export follow a remote provider? | Not in what we saw. Exporting `[site1]Inverters/Inv1/ACPower_kW` and `[site1]Inverters/Inv1` from the hub returned `"tagType": "Unknown"`, the answer for a path that does not exist (finding 25), although Designer showed the tag. The cause is not established; my guess is that the export reads only tag definitions the gateway itself owns. There is no REST route to read a tag's value (finding 17), so a remote tag's live value can only be checked in Designer or a Perspective session. | Generator existence checks: do not test a remote provider's tags through the hub's export |
| 40 | Does the simulated clock stay in step with the wall clock? | Not on this PC. Docker Desktop shows the `sim` container last started 15 hours earlier, with `SIM_START` set to 2026-10-05T17:00:00Z, so a clock running in step would read about 08:00Z (night). Live readings the same afternoon were GHI about 605 W/m2, POA about 725, direct beam 793, and diffuse 123, falling about 2.5 W/m2 a minute over two minutes: a clear afternoon sky, not a cloud (a cloud would drop the direct beam and raise the diffuse share). The clear-sky model gives GHI 652 at 21:00Z and 485 at 22:00Z, which puts the simulated time near 21:15Z on Oct 5, about four hours after the start. Probable cause, not verified: the simulator steps its clock with `time.monotonic()`, which on Linux does not count time the machine spent asleep, so the simulated day stalls while the PC sleeps. | ADR 0013 consequences; the cold-start checklist (restarting `sim` puts the plant back at its start time) |
| 41 | How much memory do the containers use? | Docker Desktop's Containers page (a screenshot Wes took) shows 3.5 GB of 15.26 GB in use across the four containers (hub, site1, postgres, sim) at about 5 percent CPU. Per-container figures were not captured, so ADR 0014's guess that the extra simulator containers are light next to the gateways is still untested. | ADR 0014 consequences (twelve containers) |
| 42 | Can the REST API create a `STANDARD` tag provider, and does a tag import at `_types_` work on a fresh one? | Yes to both. A provider created with the hub's `default` provider's own `config` (profile type `STANDARD`) came up `Running`, and `POST /tags/import?provider=<name>&path=_types_&collisionPolicy=Abort` with `{"tags": [<one type>]}` created the type. Four providers (`System`, `default`, `site1`, and the scratch one) coexisted; Maker's limit above four is still untested. The scratch provider was deleted through `POST /resources/delete/ignition/tag-provider`. | Generator (OEM providers, ADR 0014 decision 5) |
| 43 | What does a fresh provider answer when its `_types_` folder is exported? | `{"name": "_types_", "tagType": "Folder"}` with no `tags` key, not `tagType: "Unknown"` (that answer is for a path that does not exist, finding 25). A dry run of `generator.import_types` left such a provider identical before and after. | `generator.import_types` (handles both answers) |
| 44 | Does `generator.import_types` create exactly the saved definitions and never overwrite? | On a scratch provider on the hub: a dry run listed the four types as missing and changed nothing; `--apply` created them, and the provider's exported `_types_` was byte-identical to `gateway/site1/udt-types.json`; a second `--apply` reported all four unchanged; an altered copy of the file (a changed expression and a removed member) was reported as drift with exit code 2 and the provider stayed identical to the saved file. Against the real site1 the dry run reported all four types unchanged. A first attempt of the test script forgot `--file` for the hub, which has no saved file of its own: the tool refused with a clear error and changed nothing. | ADR 0014 consequences (generator work); the factory-reset rebuild |
| 45 | Does an OPC connection created through the REST API without a key store password work? | No. With the `security` group as `{"certificateValidationEnabled": true, "keyStoreAlias": "client"}` and no `keyStoreAliasPassword`, the gateway accepted the body but the connection never became healthy: its status read "Unable to retrieve KeyPair for alias 'client'. Incorrect password?" and its uptime check read "not connected", although security mode is None. Leaving out the whole `security` group, or the alias, gave other errors (a null `getSecurity()`, a null string trim). Adding `keyStoreAliasPassword` as the gateway's own encrypt-route output for the plain value `password` made the connection healthy and connected (checked with the generator's real body, on the hub, to `sim:14840`). The value `password` is not on Ignition's 8.1 or 8.3 OPC UA documentation pages, which state no default; it came from a web search summary of unnamed sources and is confirmed only by this test. The live site1 connection holds ciphertext tied to site1's own key, which is not copied. | `generator.build` (`OPC_KEY_STORE_PASSWORD`); README known limits |
| 46 | How does a resource report that it is ready? | Through health checks. A Historian provider has one (`status`, "Running"). An OPC connection has two: `status` (is its configuration usable) and `uptime` (is it connected). A connection to `sim:14840` had both healthy. A connection to a host that does not exist had `status` false ("no-such-host") and `uptime` "not connected", and the generator's `wait_for_healthy`, which now needs every check healthy, timed out as it should. Waiting on `status` alone returned before a connection was up. | `generator.apply` (the wait before the instances are imported) |
| 47 | Can the REST API create the SQL Historian provider? | Yes. A scratch provider on site1 built from the generator's body (`SqlHistorian`, database `fleetdb`, monthly partitions, pruning on at one month) reported Running at once, kept its settings exactly, and was deleted with `POST /resources/delete/com.inductiveautomation.historian/historian-provider`. The real `Historian` provider's signature did not change. It needs the `fleetdb` connection to exist (not tested without it). | `generator.connections` |
| 48 | Does an already-commissioned hub re-read `GATEWAY_NETWORK_WHITELIST` from its environment when it restarts? | Observed yes. After the compose list changed from `site1` to `site1,site2` and the hub container was recreated, the hub's stored Gateway Network `whitelist` read `site1,site2`, and Wes had not edited it (he found site2 already listed). One observation: the other direction, editing the list on a running hub, was not tested. | `docker-compose.yml` comment; CLAUDE.md |
| 49 | Does a new site gateway join the hub from its compose environment alone? | Yes. `site2`, on a fresh volume with `GATEWAY_NETWORK_0_*` from compose, appeared in the hub's incoming connections, and the hub listed its providers (`System`, `default`) with no approval step under the `SpecifiedList` policy. Its API key was rejected (HTTP 403) on the first try, which needs its security level on the key and the Gateway Write Permissions setting. | Site 2 rehearsal |
| 50 | Does `generator.providers` reproduce the hand-built remote provider? | Yes. A dry run against the hub reported Wes's `site1` provider unchanged. `--apply` created the `site2` provider, which reported Running, and a second run reported it unchanged. The hub saw 1 tag through it (site2 has no tags yet). | `generator.providers` |
| 51 | Can the generator rebuild a site gateway from an empty one? | Yes, on site2 (fresh volume, 2026-10-06): `connections` (fleetdb and Historian), `import_types` (four types from site1's saved file), `apply` (8 devices, the OPC connection, 9 instances), and `providers` (the hub's remote provider), in sequence with no warnings and no hand edits. A second pass reported everything unchanged. Site 2's overview read 8/8 devices healthy, both historians were Running, the hub saw 147 tags through `[site2]` (121 through `[site1]`; two more inverters add 26), and `sim2` served 1250 kW per inverter and 7.50 MW at the meter at clipping. The manual steps were the license token, the `API_RW` level, the write permission, and the key (a key without the level on it and the write permission got HTTP 403). | The factory-reset rebuild; ADR 0014 |
| 52 | Can one Perspective project serve sites with different numbers of inverters? | Yes. An expression binding whose expression is the constant `1`, with a script transform that calls `system.tag.browse("[default]Inverters")` and returns the list, built the Overview's flex-repeater instances and the Trends chart's pens when the page loaded. The same deployed files showed four inverter cards and four pens on site1 and six of each on site2, with 30 minutes of history on site2's chart (read from the rendered page in the built-in browser). A script transform's code is the body of a Jython 2.7 function (the header is the gateway's). If the binding fails the list is empty, so the failure is visible. Not tested: whether the list updates while a page stays open when an inverter is added. | Layer Card 2; ADR 0014 decision 7 |
| 53 | Is there a built-in tag for the gateway's own name? | Yes. `[System]Gateway/SystemName` exists on site1 and site2 (the REST client's `provider` option reads the System provider) and the header bound to it showed `site1` and `site2`. | The Header view |
| 54 | Does `generator.import_types --replace TYPE` replace exactly the named type? | Yes. On a scratch provider holding an older PlantController (no `Status` member) and an older Weather: a dry run listed the one difference and changed nothing; `--apply` with the collision policy `Overwrite` replaced only PlantController; Weather, not named, stayed older and was still reported as drift (exit 2); naming both left the provider byte-identical to the saved file. | 55 | Does a UDT change made on one gateway reach another, and does the Controller page follow? | Yes. Wes added the `RatedMW` member to PlantController in Designer on site1; `export_types` saved it (8 lines, settings identical to `POI_MW` apart from name and path); `import_types site2 --replace PlantController --apply` replaced site2's type, and a following dry run reported all four types unchanged. In the browser the Controller page read "0 to 5.0" on site1 and "0 to 7.5" on site2, from the same project files. | The fleet UDT workflow |
| 56 | Does a child project need its parent on the same gateway, and what happens when an existing project gets a new parent? | (a) `fleet` (parent `core`) deployed to the hub before `core` existed there: the gateway listed it, but Perspective answered 404 "project does not exist"; after `core` was deployed and a project scan ran, `fleet` loaded and resolved `Kpi` from `core`. (b) The existing `site` project on site1 and site2, overwritten with `parent: core`: the gateway reported the parent and the chain (`/projects/parents/site` listed `core`), yet the running project showed none of the inherited views (the browser console said `"Kpi" does not exist`), through a rescan, a redeploy, and an enabled off-and-on toggle with every property preserved. The same files as a brand-new project resolved at once. Renaming the old project aside (`site_old`) and importing a fresh `site` fixed both gateways. (c) `PUT /projects/{name}` with only `enabled` reset the project's parent and title, so a toggle must send every property. `site_old` remains on site1 and site2 as the pre-inheritance copy. | `generator.deploy_project --recreate`; `generator.deploy_all`; Layer Card 3 |
| 57 | Can an indirect tag binding fill the provider name, and can the hub find its own sites? | Yes to both. A card view with a `site` parameter and indirect tag bindings such as `[{site}]Meter/POI_MW` read `[site1]` and `[site2]` through the hub's remote providers. A script transform calling `system.tag.browse("")` returned the hub's providers (`System`, `default`, `site1`, `site2`), so the list of sites is the list of providers minus the hub's own two, and `system.tag.readBlocking` over the remote paths summed the fleet's output and rating. The fleet page read 11.10 MW output, 12.5 MW rating, and 2 sites, with one site at 71 percent of its rating under a cloud and the other at 100 percent. | The fleet views; OEM sites will appear as `oem1` to `oem6` providers |

## How the checks ran

Findings 36 to 39 used short Python snippets run in a scratch session through `generator.gateway.RestGateway`, which reads the
hub's API key from the gitignored `.env`. The snippets were not saved in the repo and have not been re-run from it. The only
change they made to the hub was the scratch provider in finding 38, which was created and deleted in the same script, which
aborts if the name already exists. The remote provider in finding 36 and the checks in finding 37 (the folder listing and the
Designer values) were done by Wes. Finding 40 was read from the simulator's published Modbus port on `127.0.0.1:15020` and
changed nothing. Findings 42 to 44 used the same kind of scratch session and a second scratch provider on the hub, `scratch-udt`,
created and deleted in the same script, which aborts if the name already exists; the hub ended with `System`, `default`, and
`site1`. Findings 45 to 47 used scratch OPC connections on the hub (`scratch-opc`, three key store variants, and one to a host
that does not exist) and a scratch Historian provider on site1, each created and deleted in its own script with the same
abort-if-the-name-exists guard. Afterwards the hub held only its built-in OPC connection and site1 only `Historian`.
