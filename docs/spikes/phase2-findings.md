# Phase 2 findings

Date: 2026-10-06. Platform: Ignition 8.3.9 Maker Edition in Docker (hub and site1 gateways), Windows 11 host. Numbering
continues from [phase1-findings.md](phase1-findings.md). These findings test the guesses listed in
[ADR 0014](../adr/0014-phase2-fleet-shape-simulators-oem-reads-inheritance-battery.md).

| # | Question | Answer | Where it matters |
|---|---|---|---|
| 36 | What do a hub's Remote Tag Provider settings look like, and can the hub's name differ from the site's provider name? | Wes built the provider by hand in the hub's Config pages. Read back through the REST API it is type `REMOTE` with `serverName` `site1` (the gateway's name on the Gateway Network), `remoteProviderName` `default`, `historyMode` `GatewayNetwork`, `alarmStatusEnabled` true, and `alarmMode` `Queried`. The hub's own name for it (`site1`) differs from the remote name (`default`), so the guess in ADR 0014 holds. Before the provider existed, `GET /gateway-network/remote-tag-providers/site1` already listed site1's two providers, `System` and `default`. The 8.3 documentation lists Name and Provider as separate fields and says a remote provider is read only by default (Default Security Zone); that last point is from the documentation and has not been tested here. | ADR 0014 decision 4; Layer Card 3 |
| 37 | Does the hub hold a copy of a remote provider's tags? | No. Listing the hub's `config/resources/core/ignition/tag-definition` folder showed only `default` and `System`, with no `site1`. In Designer, Inv1's `ACPower_kW` read about 1,100 kW on the hub and the same on site1. The provider's `tagCount` metric reads 121, and a scratch provider created seconds earlier showed 121 as well, so it counts what the hub can see through the link and not tags it stores (my reading of the metric). | Layer Card 3 (how the hub sees the fleet) |
| 38 | Can the REST API create a remote tag provider? | Yes. `POST /data/api/v1/resources/ignition/tag-provider` with a list holding `{name, enabled, description, config}` created a scratch provider, `scratch-remote`, using the hand-built provider's own `config` as the body. It reported healthy (`Running`) on the first check and showed 121 tags. It was removed with `POST /resources/delete/ignition/tag-provider` and `{name, signature}`, and the hub went back to `System`, `default`, and `site1`. The provider resource type offers three kinds: `MANAGED`, `REMOTE`, and `STANDARD`. Not tested: creating `STANDARD` providers (the OEM sites' own providers) and whether Maker limits how many providers one gateway may have. | Generator (Site 2 and OEM providers); ADR 0014 decisions 4 and 5 |
| 39 | Does the REST tag export follow a remote provider? | Not in what we saw. Exporting `[site1]Inverters/Inv1/ACPower_kW` and `[site1]Inverters/Inv1` from the hub returned `"tagType": "Unknown"`, the answer for a path that does not exist (finding 25), although Designer showed the tag. The cause is not established; my guess is that the export reads only tag definitions the gateway itself owns. There is no REST route to read a tag's value (finding 17), so a remote tag's live value can only be checked in Designer or a Perspective session. | Generator existence checks: do not test a remote provider's tags through the hub's export |
| 40 | Does the simulated clock stay in step with the wall clock? | Not on this PC. Docker Desktop shows the `sim` container last started 15 hours earlier, with `SIM_START` set to 2026-10-05T17:00:00Z, so a clock running in step would read about 08:00Z (night). Live readings the same afternoon were GHI about 605 W/m2, POA about 725, direct beam 793, and diffuse 123, falling about 2.5 W/m2 a minute over two minutes: a clear afternoon sky, not a cloud (a cloud would drop the direct beam and raise the diffuse share). The clear-sky model gives GHI 652 at 21:00Z and 485 at 22:00Z, which puts the simulated time near 21:15Z on Oct 5, about four hours after the start. Probable cause, not verified: the simulator steps its clock with `time.monotonic()`, which on Linux does not count time the machine spent asleep, so the simulated day stalls while the PC sleeps. | ADR 0013 consequences; the cold-start checklist (restarting `sim` puts the plant back at its start time) |
| 41 | How much memory do the containers use? | Docker Desktop's Containers page (a screenshot Wes took) shows 3.5 GB of 15.26 GB in use across the four containers (hub, site1, postgres, sim) at about 5 percent CPU. Per-container figures were not captured, so ADR 0014's guess that the extra simulator containers are light next to the gateways is still untested. | ADR 0014 consequences (twelve containers) |
| 42 | Can the REST API create a `STANDARD` tag provider, and does a tag import at `_types_` work on a fresh one? | Yes to both. A provider created with the hub's `default` provider's own `config` (profile type `STANDARD`) came up `Running`, and `POST /tags/import?provider=<name>&path=_types_&collisionPolicy=Abort` with `{"tags": [<one type>]}` created the type. Four providers (`System`, `default`, `site1`, and the scratch one) coexisted; Maker's limit above four is still untested. The scratch provider was deleted through `POST /resources/delete/ignition/tag-provider`. | Generator (OEM providers, ADR 0014 decision 5) |
| 43 | What does a fresh provider answer when its `_types_` folder is exported? | `{"name": "_types_", "tagType": "Folder"}` with no `tags` key, not `tagType: "Unknown"` (that answer is for a path that does not exist, finding 25). A dry run of `generator.import_types` left such a provider identical before and after. | `generator.import_types` (handles both answers) |
| 44 | Does `generator.import_types` create exactly the saved definitions and never overwrite? | On a scratch provider on the hub: a dry run listed the four types as missing and changed nothing; `--apply` created them, and the provider's exported `_types_` was byte-identical to `gateway/site1/udt-types.json`; a second `--apply` reported all four unchanged; an altered copy of the file (a changed expression and a removed member) was reported as drift with exit code 2 and the provider stayed identical to the saved file. Against the real site1 the dry run reported all four types unchanged. A first attempt of the test script forgot `--file` for the hub, which has no saved file of its own: the tool refused with a clear error and changed nothing. | ADR 0014 consequences (generator work); the factory-reset rebuild |

## How the checks ran

Findings 36 to 39 used short Python snippets run in a scratch session through `generator.gateway.RestGateway`, which reads the
hub's API key from the gitignored `.env`. The snippets were not saved in the repo and have not been re-run from it. The only
change they made to the hub was the scratch provider in finding 38, which was created and deleted in the same script, which
aborts if the name already exists. The remote provider in finding 36 and the checks in finding 37 (the folder listing and the
Designer values) were done by Wes. Finding 40 was read from the simulator's published Modbus port on `127.0.0.1:15020` and
changed nothing. Findings 42 to 44 used the same kind of scratch session and a second scratch provider on the hub, `scratch-udt`,
created and deleted in the same script, which aborts if the name already exists; the hub ended with `System`, `default`, and
`site1`.
